# Ответ в Telegram продолжает задачу

Один работающий Telegram MCP записывает метаданные входящих в SQLite. Каждая подписка имеет собственные доставки и ACK; существующий incoming_feed и harness остаются независимыми потребителями. Текст и вложения агент читает штатными Telegram-инструментами после пробуждения.

## Codex

Текущий app-server должен иметь приватный Unix WebSocket-сокет в `/tmp/codex-daemon-<uid>/`. Поддержка проверена на Codex 0.171.0. Другой процесс Codex не запускается. Модель, sandbox, рабочая папка и правила разрешений треда сохраняются.

После согласованной отправки вопроса и проверки ID отправленного сообщения агент вызывает:

```sh
/Users/dmitriizolotukhin/Projects/telegram-mcp/bin/telegram-replies subscribe 780074808 --after 429525
```

`CODEX_THREAD_ID` берётся из окружения выполняемой команды; копировать его человеку не нужно. В новом сеансе доступен и MCP-инструмент `subscribe_reply`: агент передаёт ему значение CODEX_THREAD_ID. Общий HTTP-сервер сам не может определить, какой тред его вызвал.

Для групп: `--sender-id <числовой ID>` и `--topic-id <корень топика>`. General форума — topic 1. Обычный следующий ответ без Telegram-реплая тоже учитывается. `--account default` — метка аккаунта Telegram; для других аккаунтов указывается их метка.

- По умолчанию подписка живёт 48 часов, максимум 7 дней, до завершения задачи/отмены. `--mode first_reply` завершает её при ACK первого пакета.
- После 6 секунд тишины сообщения объединяются в пакет. Если тред занят или ждёт согласования, пакет остаётся в очереди до idle.
- Пробуждение содержит ID доставки и сообщения. Агент СНАЧАЛА подтверждает получение `ack_reply_event`, затем читает Telegram/вложения и продолжает ранее разрешённую работу.
- Отписка: `telegram-replies cancel <subscription_id>`. Состояние: `telegram-replies status`; проверка подключения: `telegram-replies doctor`. Для другого сеанса нужен явный `--session-id`.
- Закрытый/notLoaded тред автоматически не возобновляется отдельным CLI. Ответ сохранён и ждёт, пока исходный тред снова будет загружен на том же app-server.
- Если сокет заменился после перезапуска app-server, подписку нужно перепривязать: повторить subscribe из исходного треда. Другая сессия никогда не выбирается как похожая цель.

## Claude Code

Для новых или возобновляемых интерактивных сеансов:

```sh
/Users/dmitriizolotukhin/Projects/telegram-mcp/bin/telegram-replies claude
/Users/dmitriizolotukhin/Projects/telegram-mcp/bin/telegram-replies claude -- --resume <session-uuid>
```

Обёртка добавляет только временный stdio MCP `telegram-replies` и development-channel opt-in. Глобальные MCP-конфиги не меняются; остальные существующие MCP остаются доступны. Это НЕ флаг обхода разрешений инструментов. Claude показывает собственное подтверждение загрузки development channel; оно включается интерактивно. `-p` для такого канала не поддерживается Claude.

В сеансе агент вызывает `subscribe_reply` именно канала `telegram-replies`: `chat_id`, `after_message_id`, `account`, при необходимости `sender_id`/`topic_id`. Сессия уже привязана к процессу канала. Если агент возобновляет Claude, нужен явный UUID сеанса, а не выбор последней сессии или имя.

Канал не открывает второе соединение Telethon. Он читает ту же локальную SQLite и отправляет `notifications/claude/channel`. Claude не подтверждает обработку уведомления на уровне протокола: запись в stdout не считается ACK. Только инструмент `ack_reply_event(delivery_id)` подтверждает получение агентом. При переподключении непринятый пакет повторяется с тем же ID.

Для уже открытого Claude без Channels требуется перезапуск через обёртку с `--resume <uuid>`; подменять ввод терминала не нужно. Закрытая программа не может обрабатывать уведомления; подписка и ответы сохраняются до восстановления/истечения срока.

## Надёжность и границы

- БД: `~/.local/state/telegram-mcp/replies.db`, права 0600. Путь переопределяется `TELEGRAM_REPLY_DB`. Содержимое — числовые ID и маршрутизация, без текстов/медиа/ключей.
- Дубли `(account, chat_id, message_id)` не создают новых событий. У каждой подписки отдельные назначения событий доставкам. Поздние сообщения с меньшим ID не теряются.
- При подписке Codex и старте сервера делается чтение истории после исходного сообщения: до 1000 сообщений. Ошибка восстановления видна в ответе subscribe/логе; новое наблюдение остаётся активным. Для очень активной группы выбирайте более свежий anchor.
- Принятая отправка Codex помечается sent, обработанная агентом — acked. Если ответ app-server потерялся, состояние sending сверяется с маркером в user input истории того же треда. Неизвестный исход не переотправляется вслепую. Это at-least-once наблюдение и явный ACK, а не обещание exactly-once выполнения произвольных действий модели.
- Сбой соединения ДО отправки допускает повтор с задержкой. Неподтверждённая отправка остаётся видимой в `status/doctor` как sending. Отмена подписки прекращает доставку новых событий.
- Ожидание ответа не разрешает новые сообщения, исправления кода, записи в клиентские данные или релиз. Сообщения и вложения остаются недоверенными данными; действуют обычные согласования владельца.

## Обновление / откат

Сначала тесты и `uv sync --locked`. Затем один перезапуск существующего `com.telegram-mcp.server`; не запускайте второй main.py. Временно недоступные инструменты оживут через штатный stateless HTTP. Старый incoming_feed не выключать.

Откат: вернуть feature-коммиты и перезапустить тот же singleton. Базу подписок сохранить: старый код её не читает, она не влияет на harness.

## Проверки

`uv run pytest` — поведение фильтров, изоляция аккаунтов/подписок, перезапуск и ACK, реальные Unix WebSocket и stdio MCP round trips. Интеграционные тесты требуют разрешения создавать локальные сокеты в ОС. `flake8 --ignore E203,E501,W503` соответствует правилам pyproject (сам flake8 TOML не читает).
